# Smart Adaptive Flashlight — NPD Demo (Physical Product)

A complete, scripted physical-product development demo built for a UVA
"New Product Development" guest lecture: a smart flashlight concept taken
from a one-paragraph "why" through spec, CAD, PCB, firmware, browser
viewers, one real design iteration, and a manufacturing-ready package —
entirely via script, with no GUI CAD or EDA tool installed.

## Why

Night-shift warehouse workers and outdoor tradespeople (electricians, HVAC
techs) need hands-free, adaptive lighting. Standard flashlights require
manual mode-switching (twisting a bezel or cycling a button sequence),
which is slow and unsafe with gloved, wet, or occupied hands. This
product's angle: **tap-based mode switching** (single tap cycles
brightness, double tap toggles strobe/SOS, detected via a hardware-level
accelerometer click engine) plus **ambient-light-adaptive brightness**
(auto-dims in bright conditions, brightens in the dark). Full narrative in
[`docs/WHY.md`](docs/WHY.md); the structured spec downstream tooling reads
is [`docs/SPEC.md`](docs/SPEC.md).

## Claude Code Skills used

Two custom skills under `.claude/skills/` drove this build, in order:

1. **[`arr-physical-spec`](.claude/skills/arr-physical-spec/SKILL.md)** —

   section format documented in the skill) plus the folder scaffold

2. **[`arr-physical-proto`](.claude/skills/arr-physical-proto/SKILL.md)** —

   viewers.

## What's actually in here

| Area | Tool (no GUI) | Output |
|---|---|---|
| CAD | [cadquery](https://cadquery.readthedocs.io/) (headless Python, OpenCascade) | `cad/step/flashlight_body_v1.step`, `cad/stl/flashlight_body_v1.stl`, `cad/dwg/flashlight_profile_v1.dxf`, `cad/boms/bom.csv` |
| PCB | [gerber-writer](https://pypi.org/project/gerber-writer/) (pure Python) + hand-written Excellon | `pcb/gerbers/*.gbr`, `pcb/gerbers/*.drl`, `pcb/bom/bom.csv`, `pcb/pick_and_place/cpl.csv` |
| Firmware | Arduino/ESP32 | `pcb/firmware/flashlight.ino` |
| CAD viewer | three.js (vendored) | `viewers/cad-viewer/` |
| PCB viewer | pcb-stackup (vendored) | `viewers/pcb-viewer/` |

### CAD

`cad/generate_cad.py` models a 130mm x 32mm, three-section (tail cap /
battery tube / head) revolved aluminum body sized to `docs/SPEC.md`'s
target dimensions exactly — bored through for an 18650 cell, with a lens
pocket and two o-ring grooves. Every dimension is a named parameter at the
top of the script, not a magic number buried in geometry calls.

### PCB

`pcb/generate_pcb.py` places real footprints — **ESP32-WROOM-32E** (MCU),
**BH1750** (I2C ambient light sensor), **LIS3DH** (I2C accelerometer, used
for its hardware single/double-click interrupt engine — chosen over a
piezo disc for much better false-positive rejection against walking/
vibration), an **AO3400** MOSFET (PWM LED driver gate) with a current-sense
resistor, and connectors for the 18650 cell, LED, and an off-board **TP4056**
charge module — on a 50mm x 30mm 2-layer board, routes orthogonal traces
between them, and emits real Gerber + Excellon files. The BOM, CPL, and the
script's own placement table all share the same reference designators and
coordinates on purpose — a mismatched CPL is a real assembly-house failure
mode, worth getting right even in a demo.

### Firmware

`pcb/firmware/flashlight.ino` is a complete, non-pseudocode Arduino sketch
for the ESP32: reads the BH1750 and LIS3DH over I2C, implements the exact
state machine from `docs/SPEC.md` (OFF→LOW→MED→HIGH→OFF on single tap,
STROBE/SOS toggle on double tap, ambient-adaptive PWM baseline, a hardware
long-press fallback switch independent of the accelerometer).

## Honest limitations

- **Scripted, not GUI-designed.** Every CAD and PCB file here was
  generated by Python scripts calling cadquery / gerber-writer — there was
  no KiCad, Fusion360, or similar tool available or installed (deliberate,
  to avoid a multi-GB GUI install for a demo). The upside: every dimension
  is a named, diffable parameter — see the v1→v1.1 iteration below.
- **Gerbers are not DRC-checked.** They are syntactically valid RS-274X
  with a correct layer stack (verified: real headers, real aperture
  definitions, real draw commands, and actually renders in
  `viewers/pcb-viewer/` via pcb-stackup against the literal files in
  `pcb/gerbers/`) — but no DRC (design rule check) engine was run, since
  there's no EDA tool installed. See `pcb/README.md` and
  `manufacturing/README.md` for the recommended JLCPCB Gerber-viewer check
  before ordering real boards.
- **TP4056 charge circuit is a module, not hand-routed** — per
  `docs/SPEC.md`'s v1 scope cut-line, it's a connector to an off-the-shelf
  breakout, not custom-routed charge-IC circuitry.
- **LED current limiting is open-loop PWM in v1** — the current-sense
  resistor (R1) is placed but not yet wired into a closed feedback loop;
  that's explicitly a v2 item.

## Viewing the files

Both viewers are static, self-contained (all JS vendored locally — no
network access needed to view), and need only a plain file server:

```bash
python3 -m http.server 8080
```

- **CAD viewer** — http://localhost:8080/viewers/cad-viewer/ — loads
  `cad/stl/flashlight_body_v1.stl` with three.js and prints its live
  bounding-box dimensions.
- **PCB viewer** — http://localhost:8080/viewers/pcb-viewer/ — fetches the
  real files in `pcb/gerbers/` and renders them client-side with
  pcb-stackup (top + bottom side SVGs).

See `viewers/README.md` for details.

## Regenerating the CAD/PCB files

```bash
uv venv
source .venv/bin/activate
uv pip install cadquery gerber-writer

python3 cad/generate_cad.py
python3 pcb/generate_pcb.py
```

## From this repo to manufactured parts

See [`manufacturing/README.md`](manufacturing/README.md) for exact,
step-by-step upload instructions:

- **`manufacturing/cad_jlc3dp/`** → [JLC3DP](https://jlc3dp.com) (3D
  print or CNC the body — settings for material/process are spelled out).
- **`manufacturing/pcb_jlcpcb.zip`** → [JLCPCB](https://jlcpcb.com) (fab +
  optional SMT assembly — settings for layer count, thickness, color, and
  the pre-order Gerber-viewer sanity check are spelled out).

## One real iteration (v1.0.0 → v1.1.0)

After the first draft, `cad/generate_cad.py`'s `WALL_THICKNESS = 1.5mm`
parameter — named and matching `docs/SPEC.md` — turned out to be dead
code: the actual body wall came out to 2.6mm because the bore was sized
only from the battery's clearance needs, ignoring the named parameter
entirely. Fixed by deriving the bore from `WALL_THICKNESS` directly (with
the old clearance number kept as an asserted safety floor). Full
before/after numbers in [`docs/CHANGELOG.md`](docs/CHANGELOG.md); compare
the `v1.0.0` and `v1.1.0` git tags to see the exact diff.
