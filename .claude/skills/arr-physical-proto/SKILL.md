# arr-physical-proto

Reads `docs/SPEC.md` and generates the first-iteration engineering
artifacts for a physical product, entirely via script — no KiCad, no
Fusion360/SolidWorks, no GUI tool of any kind. Every output is either
plain text (Gerber/Excellon/DXF/CSV/ino) or generated by a Python CAD
library (cadquery or build123d) run headlessly.

## Preconditions

- `docs/SPEC.md` exists and follows the `arr-physical-spec` format
  (Problem / Target User / Form Factor & Target Dimensions / Power Budget /
  MCU-Sensor Choice / Interface Behavior / BOM Cost Target / v1 Scope
  Cut-Line).
- Folder scaffold from `arr-physical-spec` exists: `cad/{boms,step,stl,dwg}/`,
  `pcb/{gerbers,bom,pick_and_place,firmware,datasheets}/`.

## What this skill produces

1. **CAD** (`cad/generate_cad.py` + its outputs)
2. **PCB** (`pcb/generate_pcb.py` + its outputs, + hand-authored BOM/CPL
   that must match, + firmware)
3. **Two viewers** (`viewers/cad-viewer/`, `viewers/pcb-viewer/`)

## Step 1: CAD

- Install a headless Python CAD kernel: try `uv pip install cadquery`
  first; if that fails to install cleanly or fails to `import cadquery`,
  fall back to `uv pip install build123d` and use that API instead. Confirm
  the import works before writing the generator around it — do not assume.
- Read the "Form Factor & Target Dimensions" section of SPEC.md for exact
  numbers (overall length/diameter, head/body/tail breakdown).
- Write `cad/generate_cad.py`: parametric model built from those numbers
  (e.g. for a cylindrical handheld: tail cap, body tube, head section,
  with wall thickness as a named parameter — don't hardcode wall thickness
  without naming it, the iteration pass later will likely need to change
  exactly this).
- Script must export, into the already-scaffolded folders:
  - `cad/step/<product>_body_v1.step`
  - `cad/stl/<product>_body_v1.stl`
  - `cad/dwg/<product>_profile_v1.dxf` (a 2D profile/section — DXF is the
    open stand-in for DWG; say so explicitly in the CAD README, DWG itself
    needs Autodesk tooling)
  - `cad/boms/bom.csv` — mechanical parts only (body, lens, tail cap,
    o-rings, battery cell, screws/fasteners if any) with rough per-unit
    costs at the BOM target volume from SPEC.md.
- Run the script. Confirm the STEP and STL files actually exist and are
  non-trivial in size (a valid STEP for a simple tube is >1KB; an empty/
  corrupt export is usually a dead giveaway at <200 bytes). Report actual
  bounding-box dimensions back out of the script (print them) so they can
  be checked against SPEC.md's target dimensions.

## Step 2: PCB

- Read "MCU / Sensor Choice" and "Interface Behavior / State Machine" from
  SPEC.md.
- Write `pcb/firmware/<product>.ino` (real Arduino/ESP32 sketch, real
  library names, implements the exact state machine from SPEC.md — no
  pseudocode, no TODO stubs for the core logic).
- Install `uv pip install gerber-writer` (pure Python, confirm import).
- Write `pcb/generate_pcb.py`: place simple rectangular footprints for each
  major component (MCU module, each sensor, LED driver MOSFET, battery
  connector) at explicit (x, y) coordinates on a defined board outline,
  route a handful of straight/orthogonal traces between them on one or two
  copper layers, and emit:
  - RS-274X Gerber files per layer into `pcb/gerbers/` (at minimum: top
    copper, bottom copper if two-layer, top silkscreen, top soldermask,
    board outline/edge-cuts)
  - an Excellon drill file into `pcb/gerbers/`
  - keep every placed component's reference designator, centroid (x,y),
    and rotation in a Python data structure the script also dumps or that
    you transcribe by hand — this is the data that must match the BOM/CPL.
- Hand-author `pcb/bom/bom.csv` and `pcb/pick_and_place/cpl.csv` so they
  reference the *exact same* reference designators and positions the
  generator script placed. This consistency is the point — a BOM/CPL/
  Gerber mismatch is a real assembly-house failure mode worth modeling
  correctly even in a demo.
- Add `pcb/README.md` stating plainly: these Gerbers are syntactically
  valid RS-274X/Excellon with a correct layer stack, but have **not** been
  run through a DRC (design rule check) engine because no KiCad/EDA tool
  is installed. Recommend uploading to JLCPCB's free online Gerber
  viewer (which includes a DRC-ish check) before ordering.

## Step 3: Viewers

- `viewers/cad-viewer/`: static `index.html` + `main.js` using three.js.
  Fetch a pinned three.js build (and `STLLoader`) into the repo (e.g. via
  `npm install three` into a throwaway location and copying the UMD/module
  build files into `viewers/cad-viewer/vendor/`, or downloading the exact
  files) so the page works from a plain static file server with **no**
  network access at view-time. The page must: load the generated STL,
  render it, and print its bounding-box width/height/depth on screen (in
  mm, matching the units used in generate_cad.py).
- `viewers/pcb-viewer/`: static page that renders the generated Gerbers in
  the browser (e.g. via the `tracespace` npm packages, bundled locally —
  `npm install` into `viewers/pcb-viewer/`, copy/bundle the needed files so
  it runs from a static server without a build step at view-time if
  possible, or document the one-time `npm install` needed before serving).
  Must actually load the real files from `pcb/gerbers/`, not a demo/sample
  set bundled with the library.

## Step 4: Manufacturing package

Not generated by this skill directly, but this skill's outputs are the
direct inputs: `manufacturing/` should bundle the final STEP/STL (for
JLC3DP) and a zipped Gerbers+BOM+CPL (for JLCPCB), with upload instructions
naming the exact JLCPCB/JLC3DP settings to pick (layer count, thickness,
color for PCB; material/process for the 3D print).

## Notes for the executing agent

- Every number that ends up in a generated file should be traceable back
  to a line in SPEC.md. If you're inventing a dimension that isn't in
  SPEC.md, go update SPEC.md first (or note the assumption inline in the
  script) rather than let the files and the spec drift apart silently.
- This is meant to be iterated on. Keep wall thickness, clearance gaps,
  and trace widths as named variables, not magic numbers buried in
  geometry calls — the whole point of scripted CAD/PCB over GUI tools is
  that the next iteration is a diff, not a redo.
